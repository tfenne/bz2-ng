# bz2-ng specification

bz2-ng is a drop-in replacement for libbz2 1.0.8 with a much faster single-threaded encoder and decoder. This document says what the library must do, how it is structured, how it is verified, and in what order it gets built. Where it states a measurement, the measurement was taken on the reference machines of §3 by the method given there.

## 1. Goals and non-goals

**Goals**

- **Drop-in.** Replacing libbz2 with bz2-ng is all a user does: same header, same symbols, same behaviour call for call, same bytes out. No recompilation of dependants.
- **Faster, never slower.** Both directions faster than libbz2 on every supported platform, at every level, for large files and for small independent streams alike.
- **General-purpose.** Large files, small streams (such as CRAM blocks of a few kilobytes), every level 1–9, all the legacy entry points.
- **Easy to adopt.** Plain C with no dependencies, built with each supported platform's usual toolchain (§4.7), usable from C, C++, Rust and anything else that binds libbz2 today.

**Non-goals**

- **Parallelism.** The encoder and decoder are single-threaded. No block-parallel modes, now or as an option.
- **A new format.** Streams are bzip2 streams; anything bz2-ng writes libbz2 reads, and the reverse.
- **Better compression by default.** The default output is byte-identical to libbz2's (§2.3). Ratio-improving modes are opt-in and belong to the extended API (§4.9).
- **Every platform libbz2 builds on.** bz2-ng supports the platforms of §4.7, chosen for where it would replace libbz2, and declines the rest: each platform is a lasting cost in testing and review.

## 2. Compatibility contract

### 2.1 API and ABI

- The public header is upstream bzip2's `bzlib.h`, unmodified, at commit `f5dfc96` of `sourceware.org/git/bzip2.git`: 1.0.8's header with its one change since, the `#include`s moved outside `extern "C"` for C++ standard libraries that object to being included inside it.
- The library exports exactly the 24 public functions of `libbz2.def` (six low-level, eight `FILE*`-layer, two buffer-to-buffer, `BZ2_bzlibVersion`, and the seven zlib-style `BZ2_bz*open/read/write/flush/close/error` wrappers), enforced by a version script, an export list, or on Windows a module-definition file that also keeps the names undecorated on 32-bit x86, as libbz2's own `libbz2.def` does.
- `bz_stream` layout, the `BZ_*` constants and return codes, `BZ_MAX_UNUSED`, and `BZ_API` (`WINAPI` on Windows) are unchanged. `EState`, `DState` and `bzFile` are private and free to change.
- `BZ_NO_STDIO` builds are supported: no `FILE*` layer, no diagnostics, and the integrator supplies `bz_internal_error`.
- `BZ2_bzlibVersion()` returns a string that begins `1.0.8, ` so that callers which parse a leading version keep working; the bz2-ng version follows the comma.
- Installed names are those of the package that bz2-ng replaces on each platform. ELF targets: `libbz2.so.1.0.8` with SONAME `libbz2.so.1.0` (Debian, Ubuntu, with their `libbz2.so.1` link) or `libbz2.so.1` (Fedora), chosen at build time, and `libbz2.so`, `libbz2.a`. macOS: `libbz2.1.0.8.dylib` under the system library's absolute install name `libbz2.1.0.dylib`, compatibility version 1.0.0 and current version 1.0.8. Windows with mingw-w64: msys2's `libbz2-1.dll`, `libbz2.dll.a` and `libbz2.a`. Windows with MSVC: vcpkg's `bz2.dll` and import library `bz2.lib`, `bz2d` in debug builds, and the static library `bz2.lib` when no DLL is built or `bz2_static.lib` beside one. Everywhere `bzip2.pc` for pkg-config. The C runtime is the toolchain's default: msvcrt or the UCRT with mingw-w64, as the msys2 environment chooses, and the UCRT (`/MD`) with MSVC. On 32-bit x86 Windows the functions are stdcall, as in libbz2's own DLL; msys2's and vcpkg's 32-bit packages declare them cdecl, and bz2-ng does not replace those.

### 2.2 Behaviour

For any sequence of calls a correct program can make, every call returns the same code as libbz2 1.0.8 and leaves `next_in`, `avail_in`, `next_out`, `avail_out` and the 64-bit totals with the same values. This includes:

- **Compression:** `BZ_RUN`, `BZ_FLUSH` and `BZ_FINISH` with input and output in pieces of any size down to zero and one byte; `BZ_PARAM_ERROR` for a `BZ_RUN` that makes no progress; `BZ_SEQUENCE_ERROR` when `avail_in` or the action changes during a flush or finish; `verbosity` left unvalidated in `BZ2_bzCompressInit`; `workFactor` validated to 0–250 (it selects nothing); a `bz_stream` that was copied after initialisation is rejected.
- **Decompression:** resumable at any input and any output byte; input consumed exactly as libbz2 consumes it; the same streams accepted and rejected, with the same error code after the same output has been delivered. That covers incomplete and oversubscribed Huffman code sets, selector-count handling as in 1.0.8, randomised blocks, block and stream CRC errors, truncated input, and `small` mode.
- **Buffers:** neither direction modifies the caller's output buffer beyond the bytes it delivers, even where `avail_out` would allow it; the differential testers compare the buffers beyond the delivered bytes, not only the delivered bytes. Neither direction reads outside `[next_in, next_in + avail_in)`. Within that range both may load a few bytes ahead of what they consume (the decoder's 64-bit refill, the encoder's run scan); those bytes are not consumed, are read again on the next call, and never affect the result. A caller that passes an `avail_in` larger than its buffer and relies on decompression stopping at the end of the stream is outside the contract: libbz2 happens never to touch the bytes after a stream's end, and bz2-ng may load a few of them, as zlib's fast inflate loop does.
- **Wrappers:** `BZ2_bzBuffToBuff*`, `BZ2_bzRead*`, `BZ2_bzWrite*` and the zlib-style functions are libbz2's own code over the new low-level functions, so concatenated streams, `BZ2_bzReadGetUnused` and `BZ_OUTBUFF_FULL` behave as before.
- **Allocation:** all memory through `bzalloc`/`bzfree`/`opaque`, allocated in the `Init` call so `BZ_MEM_ERROR` appears where callers expect it. The only mutable process-wide data are the cached CPU feature mask and the dispatch pointers, which are written once in a way that is safe under concurrent first use. An allocator that returns memory aligned only to 4 bytes, which is enough for libbz2, must remain enough: the state is aligned internally.
- **Diagnostics:** the decoder's output on stderr matches libbz2's at every `verbosity`; the encoder's per-block and CRC lines match (§2.5 lists what is not reproduced).

### 2.3 Output

Compressed output is byte-identical to libbz2 1.0.8's for the same input, level and call sequence. Block boundaries therefore follow libbz2's rule exactly, including under `BZ_FLUSH`.

There is one exception. A block that is exactly periodic after run-length encoding (the block is some string repeated a whole number of times; input of all zeros produces these) has several valid `origPtr` values. libbz2's choice depends on which of its internal sorters ran; bz2-ng always writes the last of the tied rows. Such streams differ in those 24 bits only and decode identically. No stream from any benchmark corpus is affected; one 600-byte CRAM test block in HTSlib's suite is, and an outside scan of real files found about 1 in 3,500 affected at level 1 (§2.5).

Every kernel tier (§4.5) produces the same bytes; output never depends on the CPU.

### 2.4 Memory

| | Documented by libbz2 | bz2-ng |
|---|---|---|
| Compression | 400 kB + 8 × block size | inside the formula at every level: 8 × block size + 109,511 bytes on 64-bit targets and 40–50 bytes less on 32-bit ones, measured |
| Decompression | 100 kB + 4 × block size | one block more by default: 100 kB + 5 × block size; an in-formula layout is a build option; see below |
| Decompression, `small` | 100 kB + 2.5 × block size | inside the formula at every level |

Memory is measured through a counting `bzalloc` in the test suite, at every level, and a build that exceeds its stated bound fails. The bounds are the same on 32-bit targets; there the peaks are 40–80 bytes lower, because the state structures hold smaller pointers.

**Decoder layout rule.** A layout with 4-byte table entries throughout needs one more block than libbz2 documents (about 900 kB at level 9). The in-formula layout stores 3-byte entries for blocks above three quarters of the level's block size and so must recover each row's output symbol from a 16 kB guess table; it walks 24 chains like the default, in memory freed by keeping that guess table in the Huffman tables' space, which nothing else uses between a block's symbol loop and the next block header. One extra block is an acceptable price for speed, but only if nothing else recovers it. Measured in the library on the reference machines, the in-formula layout runs within 2% of the 4-byte layout's speed on Granite Rapids and at its speed on blocks of at most three quarters of the block size everywhere, but on full-size blocks it is 1–3% slower on the M4 and 5–7% slower on Zen 5 and Graviton4; the remaining cost is the 3-byte walk step and, on Graviton4, the 3-byte table build. So the 4-byte layout is the default and is listed in §2.5. The in-formula layout stays available as a build option for callers that size memory pools by libbz2's formula. A cache-line-aligned 3-byte table was tried and does not fit the formula (42.9 kB of padding at level 9 against 12.2 kB spare); it gains 2–4% on Graviton4 only.

## 3. Performance requirements

Output and memory are fixed by §2, so "better" is speed. The reference is libbz2 1.0.8 built with the same compiler at its own flags, measured single-threaded in the same process on the same streams.

**Requirements**

1. **Never slower.** For every file in the benchmark corpus (`data/README.md`), every level 1–9, both directions, every supported platform and compiler: bz2-ng at its shipping configuration is at least as fast as libbz2.
2. **Small streams.** The same holds for independent streams from 1 kB to 64 kB, each with its own `Init` and `End`.
3. **Call pattern.** With caller buffers of 64 bytes or more, the legacy API runs within 10% of whole-buffer speed in both directions.
4. **No regression.** Every optimisation lands with a benchmark it must not regress; the benchmark suite runs on the reference machines for each release candidate.

**When a change gains in one place and loses in another.** The pairings that count most are clang on AArch64 and gcc on x86-64. A small loss with gcc on AArch64 or with clang on x86-64 is acceptable in exchange for a gain on one of those pairings, and is recorded with its figures. Requirement 1 holds on every pairing regardless.

**Where the library stands**

Measured at level 9 through the legacy API with the shipping configuration (the default decoder layout), MB/s with the multiple of libbz2 built by the same compiler, on the pairing that counts most for each machine, on the published corpora of `data/`.

| Data | M4 Max, Apple clang enc / dec | Zen 5, gcc enc / dec | Granite Rapids, gcc enc / dec | Graviton4, clang enc / dec |
|---|---|---|---|---|
| MC:Z, 640 kB streams | 72.2 (6.9×) / 480 (4.1×) | 74.5 (8.8×) / 457 (4.9×) | 61.0 (8.9×) / 282 (4.3×) | 52.6 (8.0×) / 240 (3.2×) |
| XA:Z, 1.65 MB streams | 74.7 (3.0×) / 296 (4.1×) | 61.2 (2.9×) / 260 (4.9×) | 49.9 (2.9×) / 176 (4.3×) | 47.6 (2.8×) / 152 (3.4×) |
| Silesia, 12 files | 65.5 (2.9×) / 243 (3.6×) | 54.3 (2.7×) / 210 (4.2×) | 44.9 (2.8×) / 148 (4.0×) | 43.7 (2.8×) / 135 (3.4×) |

Requirement 1 holds in every cell measured, including 16 kB streams, both decoder layouts and both compilers on each server; the lowest multiple is 1.56 (Graviton4, clang, MC:Z in 16 kB streams, decompression). Three things qualify the table. With gcc on x86-64 the library runs at 0.87–0.95 of its clang build for compression and, since M3c, 0.95–1.04 for decompression (it was 0.78–0.97; the one cell at 0.95 is Granite Rapids decoding XA:Z in 16 kB streams, and what remains there is gcc 13's register allocation in the symbol loop, which gcc 16 does better). On Graviton4 large-block decompression has been measured in two states of the machine: on 4 October libbz2 and bz2-ng both decoded XA:Z and Silesia more slowly there, libbz2 by about a third, which put those multiples at 3.9–4.5. The cause is not established; it was not the kernel build, which was the same on both days. And the legacy API costs the encoder nothing at calls of 5,000 bytes or more.

For scale, bzip2 level 9 output on these sets is 20–32% smaller than libdeflate's at gzip level 5, which compresses two to seven times faster than bz2-ng and decompresses five to eleven times faster.

## 4. Architecture

### 4.1 Shape

```
bzlib.h            upstream bzip2's public header, unmodified (1.0.8 plus its one later fix)
legacy drivers     libbz2's compress and decompress state machines, kept line for line
stdio layer        libbz2's bzRead/bzWrite/bzopen wrappers and BuffToBuff, unmodified in logic
block encoder      input stage → least rotation → sorter → MTF and zero runs → Huffman → bit output
block decoder      header parser → symbol loop → table build → inverse-BWT walk → un-RLE1 and CRC
kernels            scalar, x86 SSE4, x86 AVX2, AArch64 NEON; selected at run time
```

**Repository layout.** The C library is self-contained in `c/` (sources, public header, tests, the bzip2 programs, its build files) and builds without reference to anything above that directory. Language bindings live beside it in the same repository: a Rust crate in `rust/` and a JNI library in `java/` (§7, M5), each compiling the C sources from `c/`.

The legacy drivers own all `bz_stream` bookkeeping. The block encoder and decoder work on caller-owned scratch memory and know nothing about `bz_stream`; they are what an extended API would call directly.

### 4.2 Encoder

- **Driver.** libbz2's state machine (states, modes, `avail_in_expect`, progress rules) unchanged.
- **Input stage.** Run-length encoding and CRC over each caller chunk in bulk, with the run state carried between calls. The last run of every call stays pending until a later byte arrives, and a unit-by-unit tail makes each block-full decision, which is what reproduces libbz2's block boundaries. Calls of a few bytes take libbz2's per-byte path.
- **Least rotation.** The block is rotated to its lexicographically least rotation so that a plain suffix sorter yields bzip2's cyclic order; exactly periodic blocks are sorted through their root.
- **Sorter.** §4.3.
- **MTF and zero runs, Huffman, bit output.** The reworked stages of the standalone encoder with identical output: change-position scan for MTF, libbz2's table selection reproduced exactly, 64-bit bit writer.
- **Output staging.** A finished block's bits are held in the tail of the sort workspace and released to the caller exactly as libbz2 releases them (whole bytes up to the end-of-block code; the remainder carried into the next block).

### 4.3 Sorter boundary

One function is the whole interface between the encoder and the sorter:

```c
int32_t bzng_bwt(const uint8_t *T, uint8_t *L, int32_t n, int32_t q,
                 int32_t *freq, int32_t *work, size_t work_ints);
```

`T` is the block's least rotation; the function writes the cyclic BWT to `L` (which may alias `T`) and the byte histogram to `freq`, and returns the row of rotation `q`, which is `origPtr`. It allocates nothing and has no global state. The workspace is `n + n/2 + 2048` ints, which is sufficient for any input.

The sorter is libsais, by Ilya Grebnov, vendored unmodified under `c/third_party/libsais/` at commit `1a696e6` (§8). What is compiled is that file with the patches in `c/third_party/libsais/patches/` applied (below); `lib/sort_libsais.c` compiles it into its own translation unit and fits it to the boundary:

- **The BWT from the final induction.** libsais sorts the suffixes of `T` in the start of the workspace in its BWT mode, whose final induction leaves in each row's entry the byte before that row's suffix, and patch `0002-bwt-row` (below) also gives the row into which suffix `q` is induced. `T` is a Lyndon word, so suffix order is rotation order: suffix 0's row is row 0 and ends with `T[n − 1]`, one narrowing copy of the other entries gives `L`, and suffix `q`'s row is the row of rotation `q`. A `T` whose least suffix is not suffix 0 is refused.
- **Nothing is allocated.** libbz2's API cannot report an allocation failure from a compress call, and libsais has no allocator hook. Its context is its 2,048 bucket counters, which are placed in the last 2,048 ints of the workspace; the rest of the workspace beyond the suffix array is its free space, `fs` ints. During a sort libsais allocates only in its recursion, at a level whose alphabet exceeds both 1,000 symbols and that level's free space. No level does so while the first level's free space is at least its length less one: a level's free space less its length never decreases down the recursion, and its alphabet is smaller than its length. The first level's length is the number `m` of LMS positions and its free space is `fs + n − 2m` ints, so with `m ≤ ⌊(n − 1)/2⌋` top-level free space of ⌊n/2⌋ − 2 is enough for every input of length `n`; the workspace leaves at least ⌊n/2⌋. Inside the translation unit `malloc` returns NULL and `free` does nothing, so a mistake in that bound would fail a sort instead of taking memory behind the caller's `bzalloc`.
- **No libsais symbol is visible.** Its public functions are declared `static` ahead of its header, so the library defines and exports none of them and cannot clash with an application's own libsais.
- **One compiler flag.** gcc on AArch64 compiles this file with `-fno-sched-spec`. gcc's first scheduling pass, which is on by default there, otherwise moves a prefetch in libsais's final induction scans above the test that guards it; for some entries the address is then far outside the arrays, and Arm cores stall for about 90 cycles on a prefetch of an unmapped address, which costs 17–35% of compression speed. With gcc on x86-64, where that pass is off by default, the flag changes no byte of the object. A source fix (an unconditional read prefetch of a clamped address, as libsais already does for its first two cursors) removes the stall under every compiler but costs clang on AArch64 about 0.5%; the flag is free, so the library keeps the flag rather than carrying that fix as a patch. A libsais release with the fix would make the flag unnecessary.
- **Patches.** Each patch in `c/third_party/libsais/patches/` is a plain unified diff of the libsais directory, applicable with `patch -p1`, whose header says what it changes, why, and the measurement behind it. At configure time CMake copies `libsais.c` and `libsais.h` into the build directory, applies the patches there in name order with `patch` (with `git apply` where there is no `patch`; with neither, configuring fails), and requires the result to match the SHA-256 sums in `patches/SHA256`, so that a patch that applies with fuzz, in part or to another libsais stops the configuration; `sort_libsais.c` includes the copy from its include path. The patched file names its patches in its first lines. A patch carries an A/B like any optimisation (§3), and one that changes what libsais needs from the workspace is a change to this section.
  - `0001-keep-lms-positions`: after the recursion the top level maps its suffix array back to positions in the block through the list of LMS positions, which libsais rebuilds with a second classification pass over the block. The patch copies the list from the first pass into the last `m` ints of the free space instead, and the top level and the recursion work in the `fs − m` ints left, wherever `fs ≥ m` (the copy lies beyond the suffix array) and `fs + n ≥ 4m`: the first level of the recursion then has `fs + n − 3m ≥ m` ints of free space, at least its length, so the argument above still rules out an allocation. Elsewhere the positions are found again. At level 9 that is every block of a 16 KiB stream and the full blocks of inputs with at most 3/8 LMS positions (XA:Z, quality strings, ten of the twelve Silesia files), not those of MC:Z (0.40). On the M4 with Apple clang 21 (5 rounds interleaved with an identical-binary control, each speed taken relative to stock libbz2's in the same process, against the same build without the patch; both builds also carried a change to the recursion's read prefetches that measured even there and is not applied): XA:Z whole 1.061, quality strings whole 1.057, Silesia 1.035, XA:Z and MC:Z in 16 KiB streams 1.057 and 1.041, faster in every round; quality strings in 16 KiB streams 1.019, inside the noise of the raw speeds, and MC:Z whole 0.987, inside the noise. Decompression is unchanged.
  - `0002-bwt-row`: libsais's BWT mode returns only the row of suffix 0, and its `bwt_aux` form adds the rows of every r-th suffix in an array outside the workspace, for which the workspace has no room. The patch adds a flag under which the final induction runs copies of the two BWT scans that note the row into which one given suffix is induced: every suffix but `n − 1` is induced into its final row exactly once, an L-type one in the left-to-right scan and an S-type one in the right-to-left scan, and `n − 1` before the first scan. It needs nothing beyond the suffix-array mode's workspace: the final induction reads `T` and writes the entries and the bucket counters in either mode. The copies run single-threaded. Measured at level 9 on the reference machines against an identical-binary control: Graviton4 with gcc 13 and clang 18 compresses MC:Z streams of 16 and 64 KiB and the MC:Z, XA:Z, quality-string and Silesia whole files 1.02× faster; Granite Rapids is even with gcc 13 and 1.02× on the MC:Z and quality whole files with clang 18; Zen 5 is even with both; the M4 with Apple clang 21 (screening, no control) 1.01–1.03×. No cell is slower; decompression is unchanged.
  - `0003-repetitive-recursion`: below the top level of a repetitive block the reduced string is sorted by bz2-ng's own recursion, `lib/sort_recursion.h` (sais-lite 2.4.1's, as the project's October sorter specialised it: 32-bit names, each scan's bucket pointer kept in a register), instead of libsais's. A block is repetitive when its reduced string has at most one distinct name per 8 entries and more than 0.42 of its first 8,192 entries are its own LMS positions (the last entry of that window counted as L-type); over every level-9 block of the MC:Z, XA:Z, quality-string and Silesia corpora that is exactly the MC:Z blocks (LMS density 0.44–0.50 in every MC:Z block, 0.19–0.41 in every other). The recursion needs at each level free space for its alphabet only, and every level has at least its length less one: the first gets what libsais gives its own recursion, and a level passes on either `fs + n − 2m`, which does not lower free space less length, or, where it keeps its list of LMS positions, at least the next level's length. The workspace is unchanged and nothing is allocated. Timed on each block's own reduced string on the M4, it takes 0.54–0.86 of libsais's recursion time on every MC:Z block and 0.75–1.48 elsewhere, which is why only repetitive blocks take it. End to end at level 9 on the reference machines against an identical-binary control, MC:Z 16 KiB / 64 KiB / whole: Graviton4 1.03× / 1.03× / 1.04× with clang 18 and 1.02× / 1.03× / 1.04× with gcc 13; Granite Rapids 1.06× / 1.05× / 1.03× with gcc 13 and 1.04× / even / even with clang 18; Zen 5 1.02× in all three with gcc 13 and 0.97× / 0.96× / 0.97× with clang 18; the M4 with Apple clang 21 1.17× / 1.21× / 1.26×. Every XA:Z, quality-string and Silesia cell is even on every machine. The loss under clang on Zen 5 is accepted under §3, since the two pairings it ranks first both gain.

libsais replaced a sorter of the project's own, derived from sais-lite 2.4.1, once its relicence made it usable. Patch 0003 brings back that sorter's recursion for repetitive blocks only. Compared at level 9 on the four reference machines with gcc and clang, at identical memory, libsais compresses general data (Silesia) and XA:Z 6–30% faster on every pairing; on MC:Z it is between 5% slower and 17% faster on the three servers and 17–23% slower on the M4.

### 4.4 Decoder

- **Header parser.** libbz2's per-bit resumable structure, reading from a 64-bit buffer. Errors are raised after exactly the bits libbz2 would have read. While the bits are held or 8 input bytes remain, the symbol map is read 16 bits at a time, a selector as a count of leading ones with the selector MTF list in one register, and code lengths as runs of unchanged length counted in one go; a code length that leaves 1–20 is left to the bit-serial path, which raises the error after the same bits. Only the Huffman tables a kept selector names are built: libbz2's encoder often leaves a group unused in small blocks and still sends its code lengths (a quarter of the tables of QUAL in 16 KiB streams). A table counts its code lengths and orders its symbols in four interleaved parts of the alphabet.
- **Symbol loop.** A fast path decodes whole 50-symbol groups when at least 160 input bytes are available (table-driven Huffman, the head of the MTF list in a vector register); an exact path handles one symbol at a time near the end of the caller's input. Both give libbz2's results, including for code sets that are not complete prefix codes.
- **Block finishing.** Table build in parts, then a multi-chain inverse-BWT walk into a pool of chunks. In the default layout every block uses 4-byte table entries and a separate symbol array becomes the walk's output pool. In the in-formula layout, blocks above three quarters of the level's block size use 3-byte entries so that the symbol array can become the pool; a mark in each entry's spare bit lets the walk take the output symbol from the guess table without checking it, and smaller blocks use 4-byte entries in the same allocation. The walk does no I/O.
- **Output.** A resumable un-RLE1 with CRC over each call's output, writing straight into the caller's buffer. The walk's output is read in pieces, one per segment and pool chunk, and un-RLE1 goes byte by byte over the last few bytes of each; a block whose segments average under 512 bytes (with the tunables below, a block of under about 37,000 rows, or 25,000 at level 1) is first copied into text order in the table's memory, which nothing uses again before the next block, and is read as one piece.
- **`small` mode.** libbz2's packed 2.5-byte table and single chain, with the fast symbol loop and a table lookup in place of the binary search.
- **Tunables fixed by measurement:** 24 chains for blocks of at least 4,096 rows and 8 for blocks of at least 1,024, in both layouts, with at least three segments per chain where the segment arrays allow, and 2 chains for smaller blocks; software prefetch in walks of 16 or more chains; and a table build that counts the block in eight parts and scatters them four at a time, on every target. None of them affects output. The lock-step loops of 8 or fewer chains keep each chain's row and write position in locals of their own. The chain thresholds were measured on the four reference machines against 24 chains from 65,536 rows and 8 from 16,384: 16 and 64 KiB streams decode up to 10% faster on the Linux boxes, most cells by 2–7%, and 2–16% faster on the M4; whole files are even to 4% faster; nothing is slower except QUAL streams of 16 and 64 KiB under clang on Zen 5, 3% slower, accepted under §3's compiler priority. Two parts, 1–7% faster than four on Graviton4 in the prototype, are not faster there in the library with clang (Silesia 2% slower) and gain under 2% in three of ten cells with gcc; on the M4 they are 7–14% slower. Eight parts against four were measured with the decoder's other changes of the same wave: on Zen 5 and Granite Rapids with gcc and clang MC streams even to 9% faster and MC whole files 1–7% faster, with XA 2–4% faster in most cells; 5–9% faster on MC and 3–6% on XA on the M4; and 16 and 64 KiB streams 1–2% slower on Graviton4 under both compilers, a cost of the eight-part count itself: the same count over the four-part scatter loses the same there. The parts are named by constant in the scatter: reached through a pass number, they changed gcc's store order and cost 5–14% on MC streams on Granite Rapids. In blocks of at most 160 symbols in use, a move past the MTF list's register head rewrites the whole tail, up to the symbols in use rounded up to 16, so that the loop runs the same number of times on every move of a block; larger blocks, mostly binary data whose moves are many and deep, keep the loop that stops at the moved entry, which a whole-tail rewrite made slower. Against the stopping loop in every block, QUAL streams of 16 and 64 KiB decode 4–6% faster on Zen 5 with gcc and clang, 2–3.5% faster on Granite Rapids, and 1–2% faster on Graviton4 with gcc and even with clang; Silesia decodes 1.6% slower with clang on Zen 5, accepted under §3's compiler priority.
- **Safety invariants** from the decoder's CVE history are enforced on every path; a fast path never reads or writes outside its buffers on hostile input.

### 4.5 Kernels and run-time dispatch

- Every ISA-specific routine sits behind a dispatch pointer that selects its implementation on first call from one cached mask of the CPU's features (`cpuid`/`xgetbv` on x86, the auxiliary vector read from `/proc/self/auxv` on Linux AArch64, `sysctl` on macOS), as libdeflate does. **The tier is chosen at run time, never at compile time**: one binary carries all tiers for its architecture.
- Each tier is its own translation unit compiled with that tier's flags; the rest of the library uses the distribution's baseline flags.
- Granularity is one call per block per stage; the decoder's symbol loop is instantiated whole per tier so the MTF head can live in a register across symbols.

| Tier | Requires | Role |
|---|---|---|
| Scalar | portable C | Fallback for any CPU, and the reference every tier is tested against |
| x86 SSE4 | x86-64-v2 and PCLMULQDQ | Floor for x86-64; within 1–3% of AVX2 |
| x86 AVX2 | x86-64-v3; VPCLMULQDQ when present | Default on current x86 |
| AArch64 NEON | NEON and CRC32; PMULL for the CRC where present | Default on AArch64 |

There is no AVX-512, SVE2 or SIMDe tier: each measured at 0–3% or less over the tiers above. An environment variable forces a tier, and on AArch64 another removes PMULL, for tests and measurement only.

CRC kernels: slice-by-16 (scalar); on AArch64 carry-less folding with PMULL where the CPU has it, the `crc32` instructions alone otherwise; carry-less multiplication folding on x86.

### 4.6 Determinism

All stages are exact integer computations. Tests require every tier available on the test machine to produce identical bytes, in both directions.

### 4.7 Portability

**Supported platforms.** bz2-ng is for the places where libbz2 is installed today, as a system or package-manager library on current hardware. A platform is supported only if CI (§6) or the milestone runs on the reference machines build and test it:

- **Full support**, where §3's speed requirement applies: Linux with glibc or musl and macOS, on x86-64 and AArch64, with gcc and clang (Apple clang on macOS); Windows on x86-64 with MSVC and with mingw-w64.
- **Correctness only**, where the suite passes and every target gives the same bytes but speed is not measured: Linux on i686, s390x, riscv64 and ppc64le, and Windows on i686 with mingw-w64. Mainstream distributions still build for these, and s390x, being big-endian, is the only target that can see a byte-order mistake.

Nothing else is supported, even where it happens to build (armv7, mips, x32, big-endian AArch64): not Windows on ARM64, the BSDs, illumos, AIX, DOS or embedded targets. A platform is added when a maintained operating-system distribution or package manager ships libbz2 there and would take bz2-ng in its place, and CI can build and test it; the request starts as an issue (`CONTRIBUTING.md`). Code, build logic and CI for an unsupported platform are not accepted.

C11, no compiler extensions without a fallback. Little- and big-endian, 32- and 64-bit: CI runs the suite on s390x (64-bit big-endian), riscv64 and ppc64le under emulation and on i686 natively (§6), and every target gives the same bytes. gcc 9 and later, clang 10 and later, and MSVC; libsais (§4.3) compiles with those and Intel's compiler and stops with an error on any other. gcc before 11 and clang before 12 have no names for the x86-64 levels, and the build gives them the levels' instruction sets one by one. A compress call uses up to about 23 kB of stack, 16 kB of it one buffer inside libsais (measured with gcc 16 on AArch64). Platforms without a vector tier run the scalar tier, as does big-endian AArch64, since the NEON tier assumes little-endian lane order. x32 (x86-64 with 32-bit pointers) builds the scalar tier only; a selection of the suite passes for it under full-system emulation, and it has not run on hardware. Windows on x86-64 builds with MSVC (cl in C11 mode, without warnings at `/W4`) and passes CI's selection of the suite on Windows itself, on every x86 tier and with the same bytes. Under cl the SSE4 tier is compiled from intrinsics alone and the AVX2 tier under `/arch:AVX2`; under every compiler, a tier file built without its instruction set fails to compile instead of building portable code under the tier's name. Windows on x86-64 also builds with mingw-w64 and passes the suite under Wine, and a program built against stock libbz2's DLL runs unchanged with bz2-ng's. Windows on i686 builds with mingw-w64 against binutils 2.34, 2.40, 2.42 and 2.44 and passes CI's selection of the suite under 32-bit Wine. The functions are stdcall there, and dlltool writes the import library from their decorated names (`BZ2_bzRead@16`), each importing the DLL's undecorated export: ld from binutils 2.40 leaves the decorated names out of the one it writes. MSVC's speed is not measured; Windows on ARM64 is out of scope. They must still meet §3, which has not yet been measured on any of them.

### 4.8 Code style

The library follows libdeflate's conventions, so that it reads like one well-known, respected codebase and can be reviewed against it: tabs at width 8, 80-column lines, kernel-style braces, one `common_defs.h` for compiler and platform abstractions, CPU feature detection and kernels in `lib/x86/` and `lib/arm/` with a small selector header per kernel family, dispatch pointers that replace themselves on first call, and template headers for per-tier instantiations. Files that are libbz2's own code, unmodified or lightly altered, keep upstream's formatting so they diff cleanly against bzip2 1.0.8, and the vendored libsais is upstream's file, never reformatted.

### 4.9 Extended API

Deferred until after the drop-in is complete (§7, M5). It adds no speed; its value is reusable contexts with input-sized memory, and options the legacy API has no slot for. The one ratio option planned is a guard that codes each block both libbz2's way and an alternative way and emits the smaller, which is never larger than libbz2 by construction and gains 0.13–0.37% for 5–9% more encode time. Everything in the extended API lives under a new symbol prefix and a separate header.

## 5. Verification

- **Differential conformance.** A tester links stock libbz2 1.0.8 under renamed symbols beside bz2-ng and drives both with identical call sequences, comparing return code, stream pointers, totals and bytes after every call. Compression: every split point for small inputs, random `RUN`/`FLUSH`/`FINISH` sequences, output space down to zero, inputs around block capacity, every level. Decompression: every input and output split for small streams, both `small` settings, mutated and truncated streams, concatenated streams through `BZ2_bzRead`, allocation failures. A generated input whose Huffman codes exceed libbz2's 17-bit limit covers the code-length limiting, which ordinary inputs seldom reach and no other differential test does.
- **Cross-decoding.** Everything bz2-ng writes is decoded by stock libbz2, and the reverse.
- **Sorter.** Output compared with an independent oracle (cyclic prefix doubling, itself checked against a naive rotation sort) on generated families: exhaustive small alphabets, every short length, Fibonacci and Thue–Morse words, de Bruijn sequences, long runs, periodic and near-periodic blocks, worst-case inputs for the workspace bound, random lengths to the maximum block. The same families run over a build of the sorter whose `malloc` aborts, so that an input for which libsais wanted memory would fail the test; and the static and shared libraries are checked to define and export no libsais symbol and to reference no allocator from the sorter's object.
- **Every tier.** All of the above run for each kernel tier the machine supports, and tiers are compared with each other.
- **Byte order and word size.** The suite runs on a big-endian and a 32-bit target under emulation, and the same generated inputs give the same bytes there as on the reference machines. On 32-bit targets a test decodes from one input buffer longer than `PTRDIFF_MAX`, call for call against libbz2.
- **Sanitisers and fuzzing.** The suites run under AddressSanitizer and UndefinedBehaviorSanitizer. Fuzz targets for the decoder, the encoder and the sorter (`c/fuzz/`, built with `BZ2NG_BUILD_FUZZ`) run differentially against libbz2 or the oracle, on every tier of the machine; each has been shown to find faults planted in the library.
- **Memory.** Counting-allocator tests against the formulas of §2.4 at every level.
- **Drop-in tests.** bzip2's own `make test`; the `bzip2` program built against bz2-ng compared with stock bzip2 across option combinations (stdout, stderr, exit status); CPython's `test_bz2` with the library preloaded; further downstream suites before release (§7, M4).
- **ABI.** The exported symbol list is checked against the 24, on Windows from the DLL's export table; `bz_stream` layout is checked by a compile-time test.
- **Code review.** Library changes are reviewed by independent reviewers against this specification and the house style (§4.8) before they merge; the differential testers, not review, are the evidence of correctness.
- **Tests generate their data.** The corpora are for benchmarks and bulk checks; unit and conformance tests build their inputs in code.

## 6. Build and continuous integration

- CMake is the build system, producing a static and a shared library, the `bzip2` and `bzip2recover` programs from upstream bzip2's unmodified sources (§2.1's commit; `bzip2` using the shared library), libbz2's `bzip2.1` manual page, and `bzip2.pc`. `cmake --install` lays them out as the platform's bzip2 package does, with `bunzip2` and `bzcat` beside `bzip2`, and a test compares the installed files with that layout (§2.1).
- The build stays simple enough for another build system to reproduce from a short description, because the bindings compile the C sources directly: a flat list of sources, per-tier compiler flags confined to the tier translation units, no generated code but the patched libsais (§4.3), which `patch -p1` makes from the vendored file, and CPU features detected at run time rather than at configure time.
- CI builds and tests with **both gcc and clang** on Linux x86-64 and AArch64, with sanitiser jobs, a `BZ_NO_STDIO` job, emulated jobs (s390x, which is big-endian, riscv64 and ppc64le, cross-compiled, their tests under QEMU), a 32-bit job (i686, run natively on the x86-64 runner), jobs with the oldest supported toolchains (gcc 9 and clang 10 with CMake 3.16, in an Ubuntu 20.04 container), a musl job (x86-64 with gcc, in an Alpine 3.23 container), a job that runs each fuzz target briefly from its generated seeds, Windows jobs (x86-64 and i686, cross-compiled with mingw-w64, their tests under Wine, 32-bit Wine for i686), i686 Windows jobs with binutils 2.40 and 2.44 (built but not run: the DLL's exports and the import library are checked), and an MSVC job (x86-64, built by the Windows runner's Visual Studio and tested there, failing on any compiler or linker warning). macOS is covered by local runs, not hosted runners. CI runs on every pull request and on each push to one, on merges to `main`, and on demand, as all its jobs or one group of them.
- CI does not repeat the whole suite. It leaves out the mutation tests; its sanitiser jobs run one vector tier without the capacity tests; the big-endian job leaves out the tests that take more than five minutes under emulation; and the x86-64 Windows job runs the heaviest decoder and capacity phases on the AVX2 tier only. Measured runner time per job, across two runs of the whole matrix: four to twelve minutes for each Linux job that runs the suite, eight to ten for each Windows job under Wine, eleven to eighteen for the MSVC job on a Windows runner (which Windows bills at twice the Linux rate), and under a minute for the `BZ_NO_STDIO`, in-formula and build-only i686 jobs. The whole suite runs on the reference machines: as built for release for every change to the library, and under the sanitisers at each milestone; it runs under emulation for a big-endian and a 32-bit target, and the long fuzzing campaigns run, at milestones too. The big-endian job is the only one that can see a byte-order mistake, since on a little-endian target every byte swap compiles away.
- A performance job on fixed reference machines compares against libbz2 for release candidates, for gcc and clang builds: the distribution's default version of each and the latest release of each.

| M5 | **Extended API and bindings.** The extended API; a Rust `-sys` crate with a safe wrapper in `rust/`; a JNI library in `java/`. | Reusable contexts and the guarded ratio mode available under the new prefix; both bindings build from the sources in `c/` and pass their own round-trip and cross-decoding tests; documented. |

**M1 outcome.** The library is in `c/`. Conformance, drop-in tests, memory and "never slower" are met on all four reference machines with gcc and clang. Speed is within 3% of the prototypes on the M4 and for Graviton4 encode; x86 encode is 3–5% under the projection of §3, and four server decode cells are at 0.83–0.92 of the one-shot prototype, which M3 takes up (walk chains, prefetch, and the gcc-specific loop shapes).

**Since M1.** The cross-review's findings are fixed. The decoder's symbol loop under gcc, 24 walk chains and walk prefetch are in: level 9 decompression of full-size blocks in the default layout is 7–21% faster on the three servers with gcc and clang and about 1% faster on the M4, with 16 KiB streams unchanged to 13% faster. The slowest of the four M1 decode cells (Granite Rapids, MC:Z, clang) is traced to the table build and recovered. Writing the table entry before the cursor gains about 8% there and costs nothing elsewhere. Loading all four cursors before any table store gains a further 14–16% there and ends a slow mode on small streams; it is neutral on the M4 and Graviton4, costs 0.4–1.2% on MC:Z with clang on Zen 5, and leaves gcc builds unchanged. Big-endian and 32-bit targets build and pass the suite (s390x, i386, armv7 and mips under emulation), with the objects of little-endian 64-bit builds unchanged. The fuzz targets exist, and a first campaign of an hour per target on AArch64 (0.7 to 0.9 million executions each) found nothing, and neither did four hours per target on Zen 5, over every x86-64 tier, and on Graviton4 (1.2 to 3.2 million executions per target and machine). The Huffman code-length limit, which no differential test reached, has a test of its own. On 32-bit targets the decoder no longer forms pointer differences past `PTRDIFF_MAX`, and x32 builds. Windows builds with mingw-w64 and passes the suite under Wine on x86-64, every tier included; the DLL exports exactly the 24 functions, undecorated, and replaces stock libbz2's DLL without relinking. MSVC builds the library, the programs, the tests and the benchmark on x86-64 without warnings at `/W4`, and CI's selection passes on Windows on every x86 tier; a tier built without its instruction set no longer compiles. The block sorter is libsais in place of the project's own, which M1 integrated (§4.3); a fuzzing campaign on that library, 24 CPU-hours per target on Zen 5 and on Graviton4 over every tier (3.7 to 8.0 million executions per target and machine), found nothing.

**M2 outcome.** The CI matrix of §6 runs green, MSVC included (14 jobs, about 146 Linux and 33 Windows runner minutes); the fuzzing campaigns found nothing. Left to M4: the Windows package's DLL name and C runtime. Not done: Windows on ARM64 (out of scope) and clang-cl.

**M3 outcome.** Requirement 1 of §3 holds with gcc and clang on every reference machine, and each change carries its benchmark. gcc 13's decoder on x86-64 went from 0.80–0.96 of the clang 18 build to 0.95–1.04; the in-formula decoder layout is 2–9% faster and the default's bound returned to 100 kB + 5 × block size, with §2.4's question closed; AArch64 decoding gained a PMULL CRC (1–3.5% on the M4) and the two-segment table build was measured and declined. **Future phases**, not scheduled: the wider MTF head and libsais's `bwt_aux` entry (deferred, not dropped).

**M4 outcome.** Installed over Ubuntu 24.04's `libbz2.so.1.0.4` and programs in fresh containers, the unmodified test suites of libarchive 3.7.2, HTSlib 1.19 and samtools 1.19.2, CPython 3.12's `test_bz2`, GNU tar 1.35, `file` 5.45 and the bzip2 package itself pass with the same results as before, nothing rebuilt, and every compressed stream byte-identical but one (HTSlib's 600-byte periodic block, §2.5). An independent run of the same seven suites on Debian 13 (libarchive 3.7.4, HTSlib and samtools 1.21, CPython 3.13's `test_bz2`, `test_tarfile`, `test_zipfile` and `test_shutil`, GNU tar 1.35, `file` 5.46 and bzip2 1.0.8-6's own tests) gave the same results before and after (issue #14). On Alpine 3.23 (musl 1.2.5, gcc 15.2), HTSlib and samtools 1.24, which Alpine does not package, were built against Alpine's libbz2 and gave the same results with bz2-ng (`-DBZ2NG_SONAME=1`) installed over it, nothing rebuilt; so did bzip2's own six comparisons, though Alpine's `bzip2` has libbz2 compiled in, so its "before" run tested Alpine's code (issue #13). The scripts and logs of both outside runs and of the Alpine scan are in the contributor's repository `YadeWira/bz2ng-dropin-checks` on GitHub. Of the 474 binaries in 249 Ubuntu packages and 609 in 219 Fedora 44 packages that link libbz2, one references private symbols: Ubuntu's `unalz`, which bundles a modified libbz2 decoder and is left to `unalz` (§2.5); of the 2,621 ELF files in the 108 Alpine 3.23 packages that depend on it, none (issue #13). `cmake --install` reproduces each platform's package layout (Debian and Ubuntu, Fedora, macOS, msys2, vcpkg), checked by the `install_layout` test on every CI platform; `bzdiff`, `bzgrep` and `bzmore` are not shipped. The header and programs are upstream's at `f5dfc96` (§2.1, D6). The benchmark runs on the published corpora in `data/`, from which §3's table is taken.

**Release checks.** `data/README.md` states each benchmark source's licence terms, and a file whose terms could not be verified is fetched rather than committed; the library contains no prototype-only code (no SIMDe).
